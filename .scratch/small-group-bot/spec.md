# QQ 小群机器人规格

Status: ready-for-agent

## Problem Statement

群成员希望在日常 QQ 群聊中与一个能理解多人上下文的助手自然交流，无需每次都 @机器人。助手应当选择性参与、回答问题和搜索公开资料，而不是对每句话机械回复或一次汇总回答多个成员。

项目已完成本机单人私聊的一次 QQ—dot—QQ 闭环，具备持续接收实现，并已移除桥接附带的已完成问答历史。群消息接入、跨事件原生上下文、群内搜索及服务器持续运行仍需要验证和实现。

首轮服务一个指定的、15 人以内的测试群，并保留现有私聊测试入口。15 人以内是本轮使用范围，不自动引入成员计数、踢人或群规模治理功能。

## Solution

通过 QQ 官方机器人接收普通群消息，桥接保存和调度新消息，经 OpenAI 隧道及 MCP 事件唤醒对应群的 dot 聊天。dot 根据群上下文选择沉默或一个回应目标，进行闲聊或公开资料搜索；桥接校验后将结果发送回原群。

每个群对应一个独立 dot 聊天，群内成员共享上下文，群与群、群与私聊相互隔离。已完成对话的上下文由 dot 保留；桥接只交付尚未读取的新消息，不反复附加已完成问答历史。

先验证官方群消息能力、dot 原生上下文、搜索和延迟，再实现完整的小群文字版并部署服务器。图片理解、语音输入与输出、人设按后续阶段加入，前期只预留必要的数据和调用边界。

## User Stories

1. 作为项目维护者，我希望只开放指定测试群，以便在可控范围内验证群聊体验。
2. 作为项目维护者，我希望保留现有私聊测试入口，以便对照检查通信链路。
3. 作为群成员，我希望机器人能读取未 @它的普通群消息，以便自然参与正在发生的讨论。
4. 作为群成员，我希望明确 @机器人时得到正常回应，以便直接提出问题。
5. 作为群成员，我希望引用机器人追问或回答它的问题时得到连续回应，以便无需机械重复 @。
6. 作为群成员，我希望机器人能选择沉默，以便不打断正常交流。
7. 作为群成员，我希望机器人一次只回应一个对象或话题，以便知道它在对谁、对什么发言。
8. 作为群成员，我希望同批多人明确提问时分别排队回复，以便问题不因批量读取而遗漏。
9. 作为群成员，我希望连续发送的短句被结合理解，以便不被拆成多个孤立请求。
10. 作为群成员，我希望机器人识别不同发言者和引用关系，以便不混淆观点与提问对象。
11. 作为群成员，我希望同群其他成员的相关发言能成为上下文，以便展开多人讨论。
12. 作为群成员，我希望群会话与其他群、私聊隔离，以便回答不混入别处的交流。
13. 作为项目维护者，我希望沿用 dot 原生上下文，以便桥接专注通信和消息交付。
14. 作为项目维护者，我希望配置主动插话概率，以便调整参与程度。
15. 作为项目维护者，我希望概率按消息批次抽样，以便消息碎片化不导致重复抽样。
16. 作为项目维护者，我希望概率为零时仍能回应明确提问，以便关闭插话而保留问答。
17. 作为项目维护者，我希望概率为一时仍允许 dot 沉默，以便不强迫每批发言。
18. 作为项目维护者，我希望开启或关闭插话冷却并设置间隔，以便适应不同群的活跃程度。
19. 作为项目维护者，我希望冷却只在主动插话成功后开始，以便沉默或发送失败不被当作发过言。
20. 作为项目维护者，我希望全局默认配置能被每群覆盖，以便独立调整各群行为。
21. 作为群成员，我希望同群回答串行处理，以便避免多个运行争抢或重复回应。
22. 作为群成员，我希望机器人发送前参考新消息，以便不插入已经过时的话题。
23. 作为提问者，我希望明确提出的独立问题不会仅因群话题变化而消失，以便稍后仍得到回答。
24. 作为提问者，我希望说“不用查了”后取消对应回答，以便停止不再需要的工作。
25. 作为群成员，我希望可以要求搜索资料，以便获得有来源的回答。
26. 作为群成员，我希望机器人对实时或不确定的事实按需搜索，以便减少无依据的回答。
27. 作为群成员，我希望搜索只使用必要关键词，以便不向搜索服务提交整段群聊或成员昵称。
28. 作为群成员，我希望搜索结果简短并可核对来源，以便判断信息可靠性。
29. 作为项目维护者，我希望区分已读与已回复，以便沉默批次不被反复唤醒处理。
30. 作为群成员，我希望未获得插话机会的消息仍能在之后提供必要上下文，以便讨论保持连续。
31. 作为项目维护者，我希望限制未读积压的时间和数量，以便恢复运行后不补聊大量旧话题。
32. 作为项目维护者，我希望过期消息仍保留记录，以便核验而不重新触发旧问题。
33. 作为项目维护者，我希望能暂停主动插话而保留明确问答，以便临时降低参与度。
34. 作为项目维护者，我希望能暂停全部回复但继续接收记录，以便恢复后按规则继续。
35. 作为群成员，我希望重复事件和重启不造成重复发送，以便群内不出现重复回答。
36. 作为项目维护者，我希望发送结果不确定时停止重发并留下记录，以便检查实际送达情况。
37. 作为群成员，我希望普通文字闲聊典型情况下尽量在十秒内回应，以便跟上讨论。
38. 作为项目维护者，我希望将搜索耗时与普通闲聊分开统计，以便正确定位性能问题。
39. 作为项目维护者，我希望桥接在服务器持续运行并在进程重启后恢复接收，以便不依赖个人电脑。
40. 作为群成员，我希望后续可以让机器人按需理解图片，以便围绕图片讨论。
41. 作为群成员，我希望后续可以发送语音并默认收到文字回答，以便使用语音输入。
42. 作为群成员，我希望后续可明确要求语音回复，以便按需要选择输出形式。
43. 作为项目维护者，我希望后续按群选择和修改人设，以便控制机器人的称呼、语气和性格。
44. 作为项目维护者，我希望人设和普通群消息不改变工具权限，以便扩展表达方式时仍保持能力范围。

## Implementation Decisions

### 架构与接入

- 延续 QQ 官方机器人、桥接、OpenAI 隧道和 dot；当前不切换 SnowLuma 或直接调用模型 API 替代 dot。
- 复用现有 QQ 接收、事件投递、MCP 工具路由、消息持久化及发送记录模块，按实际需要修改接口，不整体重建。
- 先验证全量群事件及携带普通消息 ID 的群回复。公开接口存在不等于当前账号权限已经可用。
- 群消息保留原消息标识、群标识、发言者标识、时间、文字，以及可获取的 @、引用和附件信息。发送目的地由服务端绑定原群，模型不能任意指定接收群。
- 每群映射独立 dot 聊天，保留跨重启所需的映射信息。现有事件订阅能否稳定进入指定同一聊天、能否隔离并发运行，先通过阶段 0 验证，不预设平台具备未验证的接口。

### 消息批次、回应目标与串行执行

- 普通消息使用固定二秒收集窗口，窗口到点交付调度，不因持续来消息而无限延长。明确 @消息尽快进入调度；已有运行时遵守同群串行规则。
- 批次保留逐条发言信息，不将多人内容拼成一个无来源问题。
- 每次回应只选择一个对象或一个话题。同批多个明确问题形成独立回应目标，按顺序分别处理和发送；普通闲聊不要求逐条补答。
- 同一群一次只运行一个回答流程。事件重投或重叠唤醒不能导致同一目标同时被领取；平台与桥接如何协同维持该边界需验证后选取最小实现。
- 发送前检查新消息。过时的普通插话放弃；明确的独立问题继续等待，除非被取消或超过平台有效回复窗口。
- 引用机器人追问、回应机器人提出的问题属于明确回应场景。引用字段的实际可用性及无引用文本的指向判断，分别由接入验证和 dot 理解决定。

### 概率、冷却与配置

| 配置 | 默认值 | 语义 |
| --- | --- | --- |
| 普通消息收集窗口 | 2 秒 | 每群固定窗口 |
| interjection_probability | 0.3 | 取值 0～1，每个符合条件的普通消息批次抽样一次 |
| interjection_cooldown_enabled | true | false 时忽略冷却间隔 |
| interjection_cooldown_seconds | 30 | 可配置，从成功主动插话起算 |
| 普通未读消息最大年龄 | 10 分钟 | 仅约束尚未交付的积压 |
| 普通未读消息最大数量 | 100 条 | 与年龄限制同时生效，保留范围内较新的消息并按时间顺序交付 |
| 暂停模式 | 正常 | 另有暂停主动插话、暂停全部回复 |
| 搜索 | 开启 | 仅公开资料 |
| 回复长度上限 | 可配置 | 受实际 QQ 接口限制；迁移前沿用现有文字上限 |

- 全局默认配置允许每群覆盖，第一阶段使用配置文件，不新增管理页面。配置由维护者修改，群成员消息不直接写入配置。
- 明确 @、引用追问及回答机器人问题不受主动插话概率和冷却限制，但遵守串行执行及平台发送限制。
- 冷却期间不进行主动插话。冷却结束后每批抽样一次，通过后 dot 仍可沉默。
- 概率零关闭普通插话；概率一允许每个合格批次参与判断，不等于每批必须发送。
- 未通过抽样的批次不因之后再次进入上下文而重复获得独立抽样机会。新批次或明确提问触发时，可一并交付保留范围内的未读消息。
- 抽样失败、dot 沉默或发送失败不启动冷却。

### 已读、待回答与发送记录

- 分开记录消息交付状态和回应目标状态。前者区分尚未交付、已读、超过积压范围；后者区分待处理、处理中、已回复、已取消、已过期和发送结果不确定。
- 工具调用失败或交付未完成不能仅因“列表被查询”就标记整批已读。引入与 dot 成功读取相匹配的明确确认语义，并测试中断后的行为。
- 已读并选择沉默是正常完成结果，不再次作为未读触发。已读批次中的其他明确回应目标仍可独立等待。
- 桥接保留消息和发送记录用于交付、去重和核验；不重新引入已完成问答的 history 拼接。
- 普通消息积压超过时间或条数范围后保留本地记录，但不再自动交付。明确待回答问题独立跟踪，超出平台回复窗口即标记过期，不改写成新问题重发。
- 暂停主动插话保留明确问答。暂停全部回复继续接收记录，但不唤醒、不发送；恢复后按积压规则处理，不集中补发旧回复。
- 沿用发送前持久化预留和发送结果记录，发送结果不确定不自动重试。避免重复发送请求不等于保证每条送达。
- 订阅失效、进程中断时的消息交付及恢复必须纳入服务器阶段验证；不得将当前“没有有效订阅就忽略入站消息”的行为误认为可靠积压机制。

### 搜索与能力范围

- 文字版仅开放闲聊、公开资料搜索及完成通信所需的 QQ 工具，不开放私人资料、本机文件访问、账号操作或代码执行给群成员。
- 成员明确要求搜索或 dot 判断实时性、事实不确定性需要搜索时均可查询。仅向搜索服务发送必要关键词，默认不发送成员昵称或整段群聊。
- 搜索结果简短并提供可核对来源。QQ 对 URL 的限制先实测，保留来源信息；需要改变展示行为时再确认，不以静默删掉来源作为验收通过。
- dot 当前搜索工具的可用性和能力限制需要实际验证；不预设已配置搜索供应商，也不自动增加付费服务。

### 图片、语音与人设扩展

- 消息内容预留附件类型、标识、来源和按需读取入口；回复保留同一回应目标下的文字或媒体输出边界。不提前实现通用插件框架。
- 图片明确被询问或 dot 判断回应需要看图时再读取，不逐张强制分析或回复。
- 语音分开实现接收识别、合成输出和媒体发送。先识别成员语音并默认文字回答；之后在明确要求或群配置允许时发送语音。
- 每群选择一个由维护者管理的人设，控制称呼、语气、性格和表达习惯。普通聊天不永久修改人设；人设不覆盖群隔离、回应目标和工具权限。
- 评估复用参考项目的图片工具契约、人设卡解析和通用音频处理模块，适配官方 QQ 和 dot。依赖 SnowLuma、DSH 或独立外部语音工具的部分不能直接视为可用。
- 保留复用代码的许可声明。识别、合成供应商和具体人设内容在扩展阶段再确定。

### 部署与性能

- 先本机验证，后迁移服务器。按实际服务器系统确定常驻方式、凭据注入、启动顺序、订阅与断线恢复；当前不假设服务器系统或公网入站配置。
- 凭据继续本地配置，不进入 Git、规格或证据输出。既有消息和证据保留，变更使用独立 Git 提交。
- 普通文字闲聊典型情况下从触发消息到群内出现回复尽量在十秒内完成，包含收集窗口。此为优化目标，不是已达成的 SLA。
- 分别测量 QQ 固定回复和 dot 简短回答；记录样本数、中位数及较慢样本或有意义的高分位，不用单次样本证明长期性能。搜索另行统计。
- 若 dot 唤醒或工具往返成为瓶颈，先展示分段数据，再讨论链路调整，不自动更换接入方案或模型服务。

## Testing Decisions

### 主验收边界

以“QQ 消息进入，经过真实事件唤醒和工具交互，结果回到原群”为主要验收边界，辅以真实 dot 同聊上下文及搜索测试。验证可观察行为，不断言内部函数调用顺序代替产品结果。

离线测试优先复用现有桥接接收函数、外部 HTTP 发送、事件回调的可替换边界；使用现有 WebSocket 假服务验证协议接收。时间和随机抽样需可控，但不为每个新模块增加专用测试接口。

### 回归依据与场景

- 现有桥接测试已覆盖白名单、原会话回复、并发和重启去重、不确定发送不重试、持续接收、状态重新加载及不返回 history。保留这些行为并增加群场景。
- 现有协议测试已模拟 QQ 握手、心跳、接收和重连；扩展普通群事件、发言者及附件字段，不依赖真实凭据执行单元测试。
- 现有 MCP 与事件测试覆盖发现、订阅、回调、读取和合成事件隔离；确保 QQ 群功能不改变原合成探针契约。
- 测试固定批次窗口、明确提问优先、同批多个独立目标、每次单目标回复、重复事件和同时唤醒。
- 用确定性随机输入测试概率零、一及中间值；测试冷却开关、边界时间、成功起算和失败不计冷却。
- 测试沉默后的已读确认、读取中断、未回应明确目标保留、两类暂停、配置覆盖和恢复无旧回复洪泛。
- 测试话题变化后放弃普通插话、明确问题保留、取消请求及超回复窗口过期。
- 测试积压年龄和数量边界、逐条身份与顺序、未读增量交付和群私聊隔离。
- 测试发送目的地绑定、重复发送阻止、未知结果停止及重启恢复。
- 图片、语音、人设阶段分别验证媒体实际可读或可听、原目标回传、按需加载及权限边界；文字占位或上传成功本身不等于媒体验收通过。

### 分阶段验收

| 阶段 | 交付 | 验收标准 |
| --- | --- | --- |
| 0：能力验证 | 指定群最小接入与有界探针 | 非 @消息固定回原群；两次独立事件同聊原生上下文；真实搜索并回传来源；固定回复及 dot 分段延迟 |
| 1：本机文字版 | 群路由、批次、状态、单目标回复、概率、冷却、暂停及配置 | 多人问题分别回答、沉默不重处理、过时插话放弃、配置边界正确、私聊及旧探针回归通过 |
| 2：服务器常驻 | 桥接及隧道常驻、恢复与运维入口 | 个人电脑桥接停止后仍可用；服务器重启后恢复接收；订阅失效与重连行为有记录；无重复或集中补发旧回复 |
| 3：扩展 | 人设、图片、语音识别、语音回复逐项加入 | 每项真实链路单独验收，沿用同一回应目标、群隔离和发送记录 |

阶段 0 的任一必要能力未通过时，保留直接证据并处理对应阻塞，不把后续文字版或部署标记完成。

## Out of Scope

- 首轮不开放任意群、公开多租户服务或自动扩群。
- 不在群聊安静时定时找话题，不做无新消息触发的自主开场。
- 不向群成员开放私人资料、本机文件、账号操作、代码执行及其他新能力。
- 不恢复桥接的已完成问答历史拼接，不实现独立长期记忆系统。
- 不移植参考项目的完整控制台、DSH 运行环境或 SnowLuma 接入栈。
- 不在前期引入通用插件系统、未选定的媒体供应商或额外收费依赖。
- 不承诺消息绝不丢失、平台历史补收、固定十秒硬时限或未验证的原生聊天调度能力。
- 本次规格发布不启动群消息测试，不部署服务器，不改变运行配置。

## Further Notes

### 当前证据边界

- 已确认的实际业务闭环是 QD-0033 单人私聊，用户收到与服务器记录一致的回复；不能将其作为群聊已验收的证据。
- 移除 history 后本地四十四项测试及运行服务返回字段检查通过，原生上下文连续事件验收尚未完成。
- 官方资料已描述全量群消息及以其 ID 被动回复的能力，当前账号和群开关仍待阶段 0 实测。
- 参考实现的语音主要包含预制音频发送和音频处理，不构成可直接复用的完整语音识别、合成方案。
- 扩展供应商、服务器环境和平台实际工具能力属于后续实施前需核实的事实，不按默认假设落代码。
